# Architecture v1.0 — Complete Specification

## 0. Обзор документа

Этот документ фиксирует архитектуру проекта версии 1.0. Архитектура разделена на несколько ключевых частей:

1. **Principles, Threat Model, and High-Level Architecture** (часть 1/3)
2. **Smart Contracts: Vault v2 + Registry** (часть 2/3)
3. **Off-Chain Layer, Risk Management, Event Processing, and Runbook** (часть 3/3)

Документ предназначен для инженеров и разработчиков, занимающихся реализацией, тестированием и обслуживанием системы.

---

## 1. Principles, Threat Model, and High-Level Architecture (Part 1/3)

### 1.1 Цели и не-цели

#### 1.1.1 Цели (must-have)

1. Средства HOT не зависят от backend. Пользователи могут выводить их через on-chain.
2. COLD полностью non-custodial. Backend/бот не нужен для распоряжения средствами.
3. Монетизация через спред buy/sell. Vault не включает on-chain комиссий.
4. Отказоустойчивость к инфраструктуре. Используем fallback и retry.
5. Безопасность управления. Governance ограничен контрактом, критичные операции под timelock.

#### 1.1.2 Не-цели (explicitly out-of-scope для v1.0)

* Собственный блокчейн / ослабление криптостойкости.
* DAO-голосование “всем миром”.
* On-chain tiered fee по monthlyVolume (и любые on-chain “бухгалтерии скидок”).
* Массовая миграция “перенести всех пользователей одной транзакцией”.

---

### 1.2 Модель доступа и идентичности

#### 1.2.1 Идентичность пользователя

* **Telegram / tg_id** используется как идентификатор аккаунта для UX, поддержки, уведомлений и доступа к функциям сервиса.
* **Право на средства** определяется **владением ключом кошелька** (адресом), который взаимодействует с Vault.

#### 1.2.2 Офисная верификация (KYC-процесс)

* Возможна офлайн-верификация (паспорт + договор с оператором) как условие доступа к расширенным функциям сервиса (лимиты/режимы/поддержка).
* Офисная верификация **не должна быть обязательным условием для вывода средств из Vault**, так как вывод осуществляется подписью владельца кошелька.

---

### 1.3 Модель угроз (threat model)

#### 1.3.1 Сценарии отказов/давления

1. **Оператор недоступен/пропал:** вывод HOT работает без оператора (emergencyWithdraw).
2. **Backend/API упал:** пользователи не теряют средства; критичные операции с Vault выполняются напрямую on-chain.
3. **Telegram недоступен/заблокирован:** доступ к средствам не должен зависеть от Telegram; допускается аварийный интерфейс (web-dapp/CLI) для взаимодействия с Vault.
4. **RPC провайдер недоступен:** клиент и backend используют fallback-пул RPC.
5. **Reorg/нестабильность сети:** события учитываются с подтверждениями, применяется reconcile.

#### 1.3.2 Предположения

* Блокчейн (L1/L2, в v1.0 тест: Sepolia) предоставляет базовую безопасность консенсуса.
* Пользователь способен подписывать транзакции своим кошельком (WalletConnect/браузерный кошелёк).
* Backend может быть временно недоступен, и это считается нормальным сценариев, а не “крайним случаем”.

---

### 1.4 Инварианты (hard rules)

#### 1.4.1 HOT-инварианты

1. **Источник истины по HOT-балансам — Vault (on-chain).**
   БД/кэш не являются авторитетом.
2. **Оффчейн-компоненты не могут украсть пользовательские средства HOT.**
   Никаких adminWithdraw/ручного “списания” из баланса пользователя.
3. **Пользователь всегда может вывести средства самостоятельно.**
   `emergencyWithdraw` не отключается, не “ставится на паузу”, не тимлочится.
4. **Governance ограничен контрактом.**
   Критичные действия под timelock, миграции только в whitelist, параметры в коридорах.

#### 1.4.2 COLD-инварианты

1. Средства всегда у пользователя.
2. Подпись всегда на стороне пользователя.
3. Backend/бот не является критичной зависимостью для распоряжения средствами.

#### 1.4.3 Монетизация-инварианты

1. Доход проекта = **спред** (buy/sell котировки).
2. Vault не содержит комиссионной логики (нет computeFee, monthlyVolume, FeeTaken).

---

### 1.5 High-level архитектура (компоненты и границы доверия)

#### 1.5.1 Компоненты системы

* **Telegram Bot**: команды, уведомления, вход в Mini App, поддержка.
* **Mini App (Telegram Web App)**: основной UI режимов COLD/HOT.
* **Fallback интерфейс (web-dapp/CLI)**: минимальный функционал для чтения состояния Vault и вывода средств (в т.ч. emergency).
* **Backend API**: котировки, ордера, кэш/индекс, интеграция с WalletConnect-сессиями (если требуется).
* **Event pipeline / indexer**: сбор on-chain событий Vault, подтверждения, idempotent обработка, reconcile.
* **PostgreSQL**: кэш/индекс/история (не источник истины по средствам).
* **RPC providers pool**: несколько независимых RPC (fallback).
* **Smart contracts**:

  * Vault v2 (HOT),
  * Registry (каталог Vault’ов, опционально).

#### 1.5.2 Границы доверия (trust boundaries)

* **Trustless зона:** Vault (on-chain) и пользовательские подписи.
* **Trusted зона (операционная):** backend, БД, сервисы котировок.
  Они могут ошибаться/падать, но не должны иметь возможности “увести деньги”.

---

### 1.6 Модель дохода через спред (концепт)

#### 1.6.1 Как формируется доход

* Backend формирует котировки **buy/sell** на основе референс-цены и применяемого спреда.
* Пользователь принимает котировку в пределах TTL.
* При успешном обмене разница курсов формирует маржу проекта.

#### 1.6.2 Где живёт спред

* Спред и котировки живут **в exchange-слое** (backend + правила риска).
* Смарт-контракт Vault **не знает** о спреде, курсах и ордерах.

## 2. Smart Contracts: Vault v2 + Registry (Part 2/3)

### 2.1 VaultV2 (основной контракт)

Назначение:

* приём депозитов в HOT-хранилище;
* учёт балансов пользователей per-token;
* обычный вывод;
* **emergencyWithdraw** (всегда доступен);
* управление режимами (pause deposit / emergency mode);
* self-migration (пользователь мигрирует сам).

### 2.2 VaultRegistry (опциональный, но рекомендуемый)

Назначение:

* хранит список Vault-инстансов по токенам/сетям;
* даёт “куда депонировать сейчас” и “какие Vault активны”;
* не хранит деньги;
* не имеет прав на переводы средств.

---

## 2.3 Роли и контроль доступа

### 2.3.1 Роли VaultV2

* **governance**: multisig (команда + хранители преемственности).
  Может менять конфигурацию, добавлять целевые Vault для миграции, назначать operator, ставить/снимать паузу депозитов, управлять maxTVL и т.п.
  Все критичные действия идут через **timelock** (см. ниже).
* **guardian**: “аварийная” роль.
  Может **только включить emergencyMode**.
* **operator** (опционально): сервисная роль.
  В v1.0 не должна иметь методов, позволяющих управлять пользовательскими балансами/выводами.

### 2.3.2 Запреты (hard constraints)

* Нет функций вида `adminWithdraw`, `withdrawTo(address arbitrary)`, `setBalance`, `seizeFunds`.
* Governance/Operator не могут “перенаправить” пользовательские средства на произвольный адрес.
* `emergencyWithdraw`:

  * не отключается;
  * не “ставится на паузу”;
  * не проходит через timelock;
  * всегда выводит **только владельцу** (msg.sender).

---

## 2.4 Режимы работы Vault (state model)

### 2.4.1 `depositsPaused`

* Когда `true`: **депозиты запрещены**, выводы разрешены.
* Это мягкая пауза для обслуживания/инцидентов без паники.

### 2.4.2 `emergencyMode`

* Когда `true`: Vault переходит в максимально безопасный режим:

  * депозиты запрещены;
  * разрешены `withdraw` и `emergencyWithdraw` (или только emergencyWithdraw — решение реализации; рекомендуем оставить и обычный withdraw);
  * любые “сервисные” функции (если появятся) выключены.
* Включение: `guardian` (и/или governance).
* Выключение: рекомендуется **не поддерживать** в v1.0, либо разрешать только governance + timelock (чтобы emergency не превращался в “тумблер туда-сюда”).

---

## 2.5 VaultV2: состояние (storage) и инварианты

### 2.5.1 Рекомендуемые структуры

* `mapping(address token => mapping(address user => uint256 balance)) balances;`
* `mapping(address token => uint256 totalAssigned);`
  (агрегатная сумма учтённых балансов, чтобы можно было проверять консистентность без обхода всех пользователей)
* `mapping(address token => uint256 maxTVL);`
* `mapping(address token => bool tokenEnabled);`

Роли/режимы:

* `address governance;`
* `address guardian;`
* `address operator;`
* `bool depositsPaused;`
* `bool emergencyMode;`

Миграции:

* `mapping(address targetVault => bool allowedMigrations);`

### 2.5.2 Инварианты (проверяемые условия)

* Для каждого token:

  * `IERC20(token).balanceOf(address(this)) >= totalAssigned[token]`
    (если меньше — ситуация критична; можно триггерить emergencyMode через внешнюю процедуру, но не обязательно делать auto-trigger в контракте)
* `emergencyWithdraw` не зависит от `depositsPaused/emergencyMode`.

## 2.6 VaultV2: функции (API контракта)

Ниже “контрактный интерфейс” как требования. Сигнатуры могут быть уточнены, но смысл фиксируется.

### 2.6.1 Пользовательские функции

#### `deposit(token, amount)`

* Проверки:

  * token разрешён и включён;
  * `!depositsPaused`;
  * `!emergencyMode`;
  * `totalAssigned[token] + receivedAmount <= maxTVL[token]`.
* Действие:

  * перевод `amount` ERC-20 от пользователя в Vault (SafeERC20).
  * увеличение `balances[token][msg.sender]` на `receivedAmount`.
  * увеличение `totalAssigned[token]`.
* Событие: `Deposit(user, token, receivedAmount)`.

#### `withdraw(token, amount)`

* Доступно всегда (включая pausedDeposits).
  (в emergencyMode можно тоже разрешать, либо ограничить до emergencyWithdraw; рекомендуем разрешать обычный withdraw тоже)
* Проверки:

  * `balances[token][msg.sender] >= amount`.
* Действие:

  * уменьшить баланс;
  * уменьшить `totalAssigned[token]`;
  * transfer токена пользователю.
* Событие: `Withdraw(user, token, amount)`.

#### `emergencyWithdraw(token, amountOrAll)`

* Всегда доступно, даже в emergencyMode (особенно в emergencyMode).
* Выводит **только владельцу** (`msg.sender`).
* Варианты интерфейса:

  * `emergencyWithdraw(token, amount)` + `emergencyWithdrawAll(token)`,
  * либо единая функция с `amount=type(uint256).max` как “all”.
* Событие: `EmergencyWithdraw(user, token, amount)`.

#### View

* `balanceOf(user, token) view returns (uint256)`
* `isTokenEnabled(token) view returns (bool)`
* `getConfig(token) view returns (maxTVL, totalAssigned, enabled)`
* `getModes() view returns (depositsPaused, emergencyMode)`
* `isMigrationTargetAllowed(targetVault) view returns (bool)`

## 3. Off-Chain Layer, Risk Management, Event Processing, and Runbook (Part 3/3)

### 3.1 Event Pipeline and Risk Management

* **Event Listener**: прослушивает события смарт-контракта Vault.
* **Event Processor**: обрабатывает события, такие как депозит, вывод, emergency-вывод и изменения.
* **Reconciliation Engine**: выполняет синхронизацию состояния между смарт-контрактом и БД.

#### 3.1.1 Особенности обработки событий

* **Идемпотентность**: события могут быть повторно обработаны, но система должна понимать, что их нельзя обрабатывать дважды.
* **Reorgs и двойное учётное начисление**: если произошёл откат блоков или события были обработаны дважды, система должна корректно их откатить и повторно записать.

---

### 3.2 Client Interfaces (Emergency Client, Web/CLI)

* **Web-доступ через мини-приложение** (web-dapp).
* Подключение через **WalletConnect** (или подобное для Web3-приложений).
* **CLI** клиент для экстренной работы с контрактами.

#### 3.2.1 Запуск CLI

```bash
$ ./cli --help
# Доступные команды:
# --check-balance --token <TOKEN_ADDRESS>
# --emergency-withdraw --token <TOKEN_ADDRESS> --amount <AMOUNT>
# --show-operator
# --show-governance
```

#### 3.3.1 Сценарии аварийных ситуаций

#### 3.3.2 Тестирование инцидентов
